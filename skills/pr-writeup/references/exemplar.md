# Annotated exemplar — what a finished write-up looks like

⚠️ **Everything below is invented.** There is no such repository, no such PR and no such depot. The
system is a fictional parcel-logistics platform — depots, delivery slips, a master table — built so
the example needs both English prose and a non-Latin script, which is where the language rule in
Step 4 of the skill actually bites. **Copy the shape, never the content.** In a repository with no
Japanese, every term below would simply be English.

The fiction: 11 commits, 64 files, `+19,741 / −188`, grouped into 7 items.
⚠️ It is one shape (n=1). It is a style reference, not a size reference and not a budget.

---

## Title

```
fix(core,api,web): 配送伝票 printed the wrong 拠点コード for all 7 depots
```

`fix` · three scopes because three parts were touched · the subject is the **measured symptom**
(what printed wrong, where, how many). Domain nouns verbatim, English around them.

---

## Description — defect, then scope

> 配送伝票 printed the **wrong 拠点コード for every depot**. The code was taken from the master
> table's display-ordering column (`DepotMaster.DisplayOrder`), which has been alphabetical since
> 2026-02-11 and was never the business code. Measured against 拠点仕様書 §4.2: **0 of 7 depots
> matched**.
>
> Auditing that bug surfaced three more defects of the same family — a value stored in two places
> where only one of them is checked, so the two drift apart and nothing reports it. All four are
> fixed here.
>
> **Ticket:** — | **Type:** 🐛 Bug fix + 🧹 Cleanup | **Review Time:** ~30 min

**S1** — "0 of 7 depots matched", with the document it was measured against.
The second paragraph explains *why one bug became four* — that is what makes a large PR reviewable.

## A change item (S2 + S3 + S4)

> ### 1. 配送伝票 showed the wrong 拠点コード — all 7 depots
>
> **Impact:** the depot code on the delivery slip, and the values derived from it, was wrong for
> every depot. 北部拠点 printed as `07`, not `02`.
>
> **Cause:** the code was derived from `DepotMaster.DisplayOrder`. That column orders pickers on
> screen; it is alphabetical and carries no business meaning. 拠点仕様書 §4.2 defines the code
> separately.
>
> **Fix:** resolve the code from `Depot.Code` through an explicit map, on both the front end
> (`depotCodeOf`) and the back end (`DepotAllocation`).
>
> ⛔ Renumbering `display_order` to match was considered and rejected: it would undo a decision from
> 2026-02-11, reorder **three pickers** that all sort by that column, and — because the seeder only
> ever inserts — a JSON edit would never reach an environment already seeded.
>
> ⚠️ **9 existing 配送伝票 on `staging` still hold the wrong code** (three already `confirmed`). They
> **do not heal by themselves** — reallocation only runs when the depot changes, so Recalculate and
> Confirm will not clear them. Environment work is out of scope here, but nobody should assume this
> PR fixed them.

Heading = symptom. Impact = a concrete wrong value (`07` instead of `02`). Cause = the actual
mechanism. Fix = where, in both layers. ⛔ = the rejected alternative with three reasons.
⚠️ = what stays broken after merge, with the reason it will not self-heal.

## An item where the fix is a removal (S2)

> ### 3. Seed row counts were recorded in two places, one of them unchecked
>
> **Impact:** anyone reading `DepotSeedContext.cs` was reading numbers **wrong in 14 of 31 cases**,
> one off by more than a factor of two (18,204 claimed against 44,930 actual).
>
> **Fix — the numbers were removed, not corrected.** Tests one directory away already own them: the
> clearest case is a test pinning `parcel_scan = 2,317` — the real value — while the comment beside
> it claimed `2,340`. A comment is a second copy that nobody guards, so the durable fix is one copy.
>
> Two tables had no owning test; both gained an assertion on an **existing** test class. ⇒ **The list
> of "numbers removed with no test to own them" is empty.** Said explicitly, because an empty list
> and a forgotten list look the same.

That last sentence is the move worth stealing: **state the empty set out loud.**

## Deliberately not built (S7)

> ### 6. Two items were deliberately **not** built
>
> **A date-range option on the 集計期間 picker.** 拠点仕様書 §4.5 allows it and it is genuinely
> missing, but shipping it now would be **worse than leaving it out**: the back end no longer
> validates this field, so a malformed value **saves successfully** and only fails when the slip is
> calculated — and a reversed range does not fail at all, it silently produces a **zero total**.
> Today the option cannot be selected, so the bad value cannot be created. It needs its own PR.
>
> **A prompt pointing users at the compact view.** The premise was wrong — the toggle already has
> both a visible label and an accessible name. `decisions/depot-view.md` records the business
> decision as **"do not add it"**. Adding copy against a settled decision is not ours to do.

## What made this body good, in one line each

1. Every claim has a number behind it.
2. Items are symptoms, not tasks.
3. The rejected option is named, with its reasons.
4. What stays broken is stated, not buried.
5. Verification is a command and a result, not the word "tested".
6. The misleading diff is defused before the reviewer opens it.
7. The reader is told what to skip.
8. What was deliberately not done gets its own section.
9. Empty sets are announced, because empty and forgotten look identical.
